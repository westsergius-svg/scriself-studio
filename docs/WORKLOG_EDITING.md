текущего текста. Главный редактор фиксирует всю ленту перед открытием окна истории.
Окно модальное, чтобы параллельный ввод не менял сравниваемую сцену.

Следующее действие на момент начала: реализовать контракт/хранение и тесты, затем окно истории,
проверить восстановление в живом редакторе и обновить эту запись результатами.

Журнал не содержит паролей. Данные доступа остаются в отдельном частном журнале.

### Промежуточный результат этапа 1

Реализованы SceneVersion, методы IProjectService, таблица scene_version и миграция
SQLite 4→5, сохранение в ZIP/recovery, ограниченное по памяти сравнение слов.
Четыре теста хранения прошли. Добавлены окно SceneVersionsWindow, ViewModel и
кнопка «Версии» в редакторе. Перед окном фиксируется вся лента, после восстановления
сцена перечитывается; просмотр без изменений сохраняет Undo.
Сейчас выполняются UI-тесты пяти тем и восстановление перед автосохранением.
Следом: полный прогон, живой Debug, справка и окончательная запись передачи.
Стабильный установщик предыдущего этапа пока не заменялся.

### Дополнительная проверка Undo и подготовка передачи

Обнаружено, что прямое присваивание RichEditor.Document сохраняет старую очередь Undo.
Восстановление теперь вызывает штатную загрузку документа со сбросом истории через
публичный LoadDocument; обычный просмотр версий её сохраняет. Добавлен тест с настоящим
EditorView и клавиатурным вводом: просмотр → Undo/Redo → восстановление → новая правка
→ Undo → запись. Профильная проверка 1/1 прошла. Прямой вызов InsertText сам по себе
не создаёт шаг отмены: в тестах пользовательского ввода использовать KeyTextInput.

Контракты, ADR 031, формат данных, CHANGELOG и справка обновлены. Новая тема справки
называется «Версии сцены»; USER-GUIDE.md заново построен tools/update-user-guide.ps1.
Окончательный Release-прогон и Debug-проверка выполняются после этой записи.

## План этапа 2 — выполнен, сохранён для контекста

Разрешение на него уже получено. Начинать с отдельного решения и тестируемого
контракта, без смены номера приложения. Конкретный первый риск: в
RichDocumentAdapter.FromFlowDocument создаются новые TextBlock без переноса Id.
Нельзя привязывать комментарии только к текущим GUID абзацев, считая их стабильными.

Порядок реализации:

1. Определить единицы привязки (существующий контракт — UTF-16), стабильные ID
   абзацев и преобразование диапазонов при вводе, вставке, удалении, разделении,
   склейке и переносе сцены. Проверить сохранность привязки через адаптер и Undo/Redo.
2. Зафиксировать модели комментария и правки, автора/дату, принятие и отклонение,
   удалённые фрагменты с оформлением. Выбрать поведение комментариев на удалённом
   тексте и при восстановлении версии; снимки версий должны включать нужные данные.
3. Добавить хранение SQLite/ZIP/recovery и миграции, затем команды и панель редактора.
4. Проверить ввод с IME, автозаглавную, орфографическую замену, несколько сцен ленты,
   Undo/Redo, перезапуск, экспорт чистой рукописи и отказ записи. Затем живой Debug
   с нулём ошибок привязки; закрыть процесс и обновить журналы.

Этап 3: см. LANGUAGETOOL-RESEARCH.md. Нужна проверенная локальная пара Java/LanguageTool,
набор реальных русских и английских примеров, привязка ответов к актуальной ревизии,
задержки и отмена, запуск/завершение процесса и комплект лицензий. Рукописи в облако
автоматически не отправлять. Подключения грамматики сейчас нет.
