# ADR 006. MCP-инструменты для агента: документация Avalonia и живой UI

Дата: 2026-09-27
Статус: принято

## Контекст

ТЗ п. 12, 15 и 58 требуют, чтобы агент проверял интерфейс, а не ограничивался успешной
компиляцией, и чтобы решения фиксировались в `docs/decisions/`. До этой записи визуальная
проверка выполнялась только через headless-рендер в тестах (`ScreenRenderTests`), а знание
об Avalonia бралось из контекста модели — это источник типичных ошибок в AXAML и
смешения API с WPF.

## Решение

Подключены два MCP-сервера. Конфигурация лежит вне репозитория, в `~/.codex/config.toml`
(пользовательская настройка, не часть проекта):

1. `avalonia-docs` — официальный сервер документации Avalonia, транспорт streamable HTTP,
   `https://docs-mcp.avaloniaui.net/mcp`. Инструменты: `search_avalonia_docs`,
   `lookup_avalonia_api`, `get_avalonia_expert_rules`, а также миграционные наборы WPF→Avalonia.
   `get_avalonia_expert_rules` возвращает правила по AXAML, property system, стилям,
   compiled bindings, MVVM и типичным ошибкам — его следует читать в начале работы над UI.
2. `avalonia-devtools` — сервер диагностики живого приложения Avalonia, транспорт stdio.
   Внутри приложения работает `AvaloniaMcp.Diagnostics`; сервер-потребитель —
   `AvaloniaMcp.Server` 0.4.0, запускаемый рантаймом .NET 10.

Приложение подключает диагностику только в конфигурации Debug:

- `AvaloniaMcp.Diagnostics` добавляется условной ссылкой на пакет при `Configuration == Debug`;
- `Program.BuildAvaloniaApp()` вызывает `.UseMcpDiagnostics()` внутри `#if DEBUG`.

В Release и в опубликованном exe диагностический сервер не стартует.

## Последствия

- Агент может читать официальную документацию и правила, а не угадывать API.
- Агент видит работающее окно: дерево визуальных и логических элементов, `DataContext`
  и публичные свойства ViewModel, значения свойств контролов, применённые стили, ресурсы,
  ошибки биндинга, сфокусированный элемент и PNG-снимок окна или контрола.
- Проверка «UI не сломан» перестаёт быть утверждением и становится измерением: например,
  `get_binding_errors` возвращает пустой список, а не молчание.
- Debug-сборка получает лишний пакет и диагностический сокет. Это осознанная плата:
  сервер не имеет аутентификации и предназначен только для локальной отладки, поэтому в
  поставляемую сборку он не попадает.
- Сервер требует рантайм .NET 10, которого нет в списке SDK проекта. Он установлен
  локально для пользователя (`%USERPROFILE%\.dotnet-sdk9`), `global.json` и целевой
  фреймворк проекта не изменялись: решение остаётся на .NET 8.
- Новые серверы подхватываются приложением Codex только после его перезапуска.

## Альтернативы

- **`Zafiro.Avalonia.Mcp` 0.1.10.** `Zafiro.Avalonia.Mcp.AppHost` работает и отвечает на
  сырые запросы по именованному каналу (проверено командой `ping`), но опубликованный
  `Zafiro.Avalonia.Mcp.Tool` 0.1.10 зависает на `list_apps` и `connect_to_app`: обработчик
  не завершается и не пишет ошибку ни в лог, ни клиенту (проверено с уровнем Trace).
  Пара «AppHost 0.1.10 + Tool 0.1.10» непригодна, поэтому от неё отказались.
- **`AvaloniaSpy` 1.8.2** и **`Keincheck.Avalonia` 0.12.0** собраны под Avalonia 12, проект
  работает на Avalonia 11.3.22 — несовместимо без миграции.
- **`Mostlylucid.Avalonia.UITesting`** не имеет цели под `net8.0`.
- **Только headless-рендер тестами.** Остаётся как автоматическая проверка раскладки
  (`ScreenRenderTests`), но не даёт доступа к живому `DataContext`, стилям и ошибкам биндинга.
