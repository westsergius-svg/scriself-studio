# ADR 035. Сохранение ревизии, общий выход из рабочего пространства и уникальные ZIP-ключи

Дата: 2026-11-17
Статус: принято; уточняет ADR 002, 005, 009, 016 и 019

## Контекст

Аудит на синтетических проектах подтвердил потерю текста ZIP при одинаковом
`scene_001`, снятие `IsDirty` с правки, сделанной во время записи, пропуск черновиков
панелей при уходе из проекта и перезапись файла вторым владельцем. Один commit
редактора не охватывает контекст сцены, архитектуру, персонажей и сюжетные линии.

## Решение

1. `IWorkspaceSaveService` в Contracts задаёт `HasPendingEdits` и `SaveAsync`.
   Реализация App координирует существующие ViewModel: фиксирует всю ленту редактора,
   контекст, архитектуру и сюжетные панели, затем записывает проект. Успех означает,
   что более новых черновиков нет. Ошибка оставляет книгу открытой.
2. Глобальное сохранение, смена/закрытие проекта, закрытие окна и запуск обновления
   используют одну границу сохранения. Каждый переход проверяет результат; запуск
   установщика происходит после сохранения, а завершение приложения — после запуска.
3. `ProjectService` последовательно выполняет операции открытия, создания, записи
   и закрытия. Редактирование не блокируется: запись получает глубокую копию и номер
   ревизии. Только совпадение ревизии после записи снимает `IsDirty` и удаляет recovery.
   Более новые правки обновляют recovery и требуют следующего сохранения.
4. `ProjectFileVersion` и `ProjectSaveRequest.ExpectedFileVersion` переносят отпечаток
   существования/SHA-256 файла. Сервис проверяет его до записи recovery, хранилище —
   до замены временного файла. Общая краткая блокировка по абсолютному пути координирует
   экземпляры Studio; конфликт возвращает `ProjectFileConflict`. Устаревший владелец
   не заменяет файл или чужое восстановление и может сохранить отдельную копию.
5. ZIP сохраняет старые `documents`/`sceneVersions` по `SourceId` и добавляет
   `documentsBySceneId`/`sceneVersionsBySceneId` по Guid, записанному как `scriselfId`.
   Старые ID сцен и глав уникальны во всём контейнере; новые и повторяющиеся получают
   ID на основе Guid. Каноническая карта имеет приоритет. Общая старая запись для
   нескольких сцен и повторяющийся Guid отклоняются вместо подстановки чужих данных.
6. Повреждённый JSON SQLite преобразуется в `Result` ошибки формата. Канонические
   документы ZIP и история проверяются без молчаливого перехода к пустому документу.

## Совместимость и последствия

Схема SQLite остаётся 6, ZIP manifest — 1. Старые карты ZIP сохраняются для Studio
1.2.0; сторонние читатели продолжают использовать плоское поле `text`. Уже утраченный
в старом неоднозначном архиве текст не восстанавливается автоматически: нужен backup.
`ExpectedFileVersion = null` сохраняет совместимость прямых вызовов хранилища, а
сервис приложения передаёт отпечаток. `SaveCompleted` описывает записанный снимок;
уход из интерфейса требует дополнительного успеха `IWorkspaceSaveService`.

Глубокий снимок и хеширование стоят памяти/времени на сохранение. Блокировка координирует
Studio по пути и не заменяет контроль версий файла для внешних редакторов. Ошибки
записи recovery логируются; если запись recovery не удалась, её наличие не обещается.

## Проверки

`SaveIntegrityTests`, `ZipIntegrityTests` и `WorkspaceSaveTests` проверяют реальные
задержанные записи, новый текст/редактуру, два сервиса, внешнее изменение, одинаковые
старые ID, повторное открытие, все панели, отказ сохранения и отказ запуска обновления.
