# Работа агентов

Правила для любого ИИ-разработчика в этом репозитории. Источник требований — ТЗ п. 4, 12,
15, 38–50, 53–58.

## Обязанности

1. Сначала прочитать контракты (`docs/CONTRACTS.md`) и связанные тесты — потом код.
2. Работать только в разрешённой области файлов и только через контракты.
3. Не создавать дублирующие модели: у сущности один владелец.
4. Не менять чужой модуль без явного задания.
5. Не добавлять зависимость UI в `Core`; `Core` не знает ни о UI, ни о DI.
6. Не удалять работающую функцию без миграционного плана.
7. Не считать задачу выполненной только потому, что проект компилируется.
8. При неоднозначности остановиться на границе контракта и сообщить о конфликте.
9. Каждое значимое решение фиксировать в `docs/decisions/`.

## Порядок работы

Перед изменениями:

- прочитать задание, контракты и применимые ADR;
- проверить фактическое состояние файлов;
- запустить относящиеся к задаче проверки;
- отделить существующие ошибки от новых.

После реализации:

- проверить критерии приёмки;
- выполнить `dotnet build`, `dotnet test`, проверку запуска приложения;
- передать результат на ревью вместе с отчётом.

Старый отчёт другого агента не заменяет проверку текущего кода.

## Обязательные проверки (ТЗ п. 15)

```powershell
dotnet restore
dotnet build --configuration Release
dotnet test --configuration Release
dotnet run --project src/ScriSelfStudio.App
```

Сборка проекта — по одному `.csproj` за раз (MSBuild не принимает два пути сразу).

## Шаблон отчёта (ТЗ п. 15, 43)

```
Изменено:
Проверено:            # «проверено автоматически» / «проверено вручную» / «не проверено»
Тесты:
Ограничения:
Следующий этап:
```

Отчёт обязан различать автоматическую и ручную проверку. Нельзя утверждать «всё
работает», если проверена только компиляция.

## Передача работы между сессиями (ТЗ п. 42, 50)

```
Задача и статус:
Версия контракта:
Изменённые файлы:
Реализованное поведение:
Выполненные проверки и результаты:
Известные ограничения:
Следующее конкретное действие:
```

Новая сессия начинает с этой записи, актуальных контрактов и состояния репозитория.
История переписки не должна быть единственным источником требований.

## Формат задания (ТЗ п. 38, 45, 53)

```
ID:
Цель и пользовательский результат:
Исходное состояние:
Прочитать:
Разрешено изменять:
Используемые контракты:
Требуемое поведение:
Обработка ошибок:
Критерии приёмки:
Команды проверки:
Что не входит в задачу:
Зависимости от других задач:
```

Задача завершается проверяемым результатом. Формулировки «сделай редактор полностью»,
«закончи ядро» недопустимы: большая функция разбивается на части — контракт и примеры,
реализация логики, тесты поведения, подключение UI, проверка общего сценария.

## Изменение контрактов (ТЗ п. 40, 48, 56)

Модульный агент не меняет публичный контракт сам. Предложение оформляется так:

```
Какого сценария не хватает:
Почему существующий контракт не подходит:
Предлагаемое изменение:
Затрагиваемые потребители:
Порядок перехода:
Проверки совместимости:
```

Решение принимает владелец контрактов, после чего обновляет контракт и уведомляет
исполнителей. Создавать локальную копию интерфейса, чтобы обойти конфликт, запрещено.

## Git (ТЗ п. 41, 49, 57)

- Одна независимая задача — отдельная ветка или worktree.
- Общие файлы solution, версии пакетов, `Contracts` и регистрация DI имеют одного
  ответственного — архитектора базы.
- Перед объединением проверяются: область изменений, совместимость с контрактами,
  сборка и тесты, отсутствие незаявленных изменений формата данных, завершённость сценария.
- Механическое принятие одной стороны конфликта недопустимо.

## Что проверяет приёмка (ТЗ п. 43)

Особое внимание: заглушки, возвращающие успех; скрытые исключения; дублирование моделей;
потеря форматирования при правке текста; порядок фоновых сохранений; неосвобождённые
подписки на события; файловые операции на UI-потоке; тесты, повторяющие реализацию вместо
проверки требований.

## MCP-инструменты (ТЗ п. 58)

Разрешено и ожидается использование двух MCP-серверов, описанных в ADR 006:

- `avalonia-docs` — официальная документация и правила Avalonia. Перед написанием AXAML,
  стилей, биндингов или контролов вызвать `get_avalonia_expert_rules`, для конкретного API —
  `lookup_avalonia_api`. Не полагаться на память модели об Avalonia и не писать API WPF.
- `avalonia-devtools` — диагностика живого приложения. Сначала запустить Debug-сборку
  (`dotnet run --project src/ScriSelfStudio.App`), затем работать инструментами сервера:
  `list_windows`, `get_logical_tree`, `get_visual_tree`, `get_data_context`,
  `get_control_properties`, `get_applied_styles`, `get_binding_errors`, `find_control`,
  `click_control`, `input_text`, `take_screenshot`.

Обязательные правила работы с диагностикой:

- сервер стартует только в конфигурации Debug;
- после проверки живой UI закрыть приложение — сервер не имеет аутентификации;
- `get_binding_errors` должен возвращать пустой список: ошибка биндинга — это дефект, а не шум;
- вывод сервера фиксировать в отчёте как «проверено вручную», отдельно от автотестов.

Пределы этой оснастки (проверено, см. `docs/TESTING.md`):

- читаются окна, визуальное и логическое дерево, свойства, стили, ресурсы, `DataContext`,
  ошибки биндинга и PNG-снимок;
- управление ограничено: нажимаются только кнопки с привязанной `ICommand`, вводится текст в
  `TextBox`, задаются скалярные свойства. Нажатие вне `Button` и выбор элемента
  `TreeView`/`ListBox` недоступны, поэтому сценарии, требующие выбора узла, через MCP
  не воспроизводятся — их закрывает автотест UI;
- сервер обслуживает одно соединение: пока приложение Codex подключено к процессу, CLI того
  же сервера к нему не подключится. Для ручных прогонов использовать CLI-режим
  (`dotnet AvaloniaMcp.Server.dll cli <метод> --pid <PID>`), не вызывая MCP-инструменты
  параллельно;
- проект можно открыть без нативных диалогов: `ScriSelfStudio.exe "<путь>.scri"`.

Конфигурация MCP хранится в `~/.codex/config.toml` и не является частью репозитория.
Добавленные серверы становятся доступны приложению Codex только после его перезапуска.

## Окружение

- .NET 10, зафиксирован в `global.json`; UI редактора использует Avalonia 12 и
  `AvaloniaRichEditor`, поэтому запускать тесты нужно на поддерживаемом .NET 10 SDK.
- Версии пакетов — в `Directory.Packages.props`. Агенты не обновляют зависимости
  самостоятельно и не добавляют альтернативные библиотеки для уже решённой задачи
  (ТЗ п. 32).
- Компилятор настроен строго: `TreatWarningsAsErrors`, анализаторы, `EnforceCodeStyleInBuild`.
