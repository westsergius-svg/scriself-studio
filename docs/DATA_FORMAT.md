# Формат проекта `.scri`

Требования: ТЗ п. 5, 13, 23, 37.

## Редактура — схема 6 (ADR 032)

`RichDocument.review` хранит режим записи, имя автора, комментарии и правки.
Данные находятся в том же JSON, что и текст сцены, поэтому включены в SQLite,
ZIP, recovery и снимки версий. У старых документов поле отсутствует и читается
как пустая редактура. Миграция SQLite 5→6 обновляет номер в копии; исходный файл
остаётся в `.bak`. Старые сборки блокируют открытие новой схемы.

Комментарии используют UTF-16-диапазоны и ID абзацев; цитата сохраняется после
удаления текста. Правка содержит исходный документ без вложенной истории и
диапазоны замены с оформлением. Повреждённые диапазоны нельзя молча отбрасывать.
Пустой текст может содержать удалённые фрагменты и комментарии: ZIP обязан
сохранить его полный документ. Экспорт читает только текущие блоки рукописи.

## Общее

Файл проекта — база данных **SQLite**, создаваемая `Microsoft.Data.Sqlite`.
Внутри хранятся метаданные проекта, структура книги, текст сцен с форматированием,
сюжетные линии, настройки проекта и версия схемы. Расширение файла — `.scri`.

## Поддерживаемые форматы файла

Приложение определяет формат по содержимому файла, а не по расширению (ADR 009):

| Формат | Признак | Чтение | Запись |
| --- | --- | --- | --- |
| Собственный (SQLite) | заголовок `SQLite format 3`, таблица `schema_info` | да | да |
| Старый контейнер | заголовок `PK`, внутри `manifest.json` и `content.json` | да | да, в тот же формат |
| Ранние модульные сборки | SQLite с таблицами `entities`/`meta` | да, импорт в текущую модель | нет (только в текущий формат) |

Расширение не определяет формат: проекты и резервные копии `.scri`, `.bak` и `.backup`
открываются по содержимому. SQLite также принимает прежнее имя таблицы шагов
`plot_line_stage`; при следующем сохранении данные записываются в актуальную таблицу
`plot_line_step`. DOCX и TXT являются форматами экспорта рукописи, а не проектными файлами.

Проект, открытый из старого контейнера, при сохранении записывается обратно в него:
`manifest.json` и `content.json` сохраняют структуру, а поля, которых нет в нашей модели
(`library`, `volumes`, служебные поля глав), переносятся без изменений. Новые сущности
получают идентификаторы вида `chapter_<Guid в формате N>` и `scene_<Guid в формате N>`;
неповторяющиеся существующие ID сохраняются (`chapter_001`). Сцены дополнительно
хранят стабильный `scriselfId` — Guid канонической модели (ADR 035).

Первое сохранение проекта в старом формате всегда создаёт `<файл>.scri.bak` с предыдущей
версией, даже если резервные копии в настройках выключены. Открытие файл не изменяет.

## Импорт раннего модульного формата

Файл ранних сборок — тот же SQLite, но с таблицами `meta`, `entities`, `relations`
и `texts`. `LegacyModularImporter` читает его и собирает текущую модель:

| Из раннего формата | Куда попадает |
| --- | --- |
| книга | серия и книга |
| глава | глава, `SourceId` сохраняется |
| сцена | сцена; `goal`/`conflict`/`result`/`dateTime` — в описание |
| текст сцены | абзацы документа (`RichDocument`) |
| персонаж | карточка персонажа (роль, мотивация, заметка) |
| сюжетная линия и её этапы | линия с этапами, сцены привязываются по `relations` |
| `plotlineId` без самой линии | линия синтезируется с именем по идентификатору |

Формат определяется по наличию таблиц `entities` и `meta`, а не по `appVersion`,
поэтому подходят все известные сборки. Импортированный проект **не перезаписывается
в исходном формате**: при первом сохранении создаётся текущий SQLite-файл, а исходник
остаётся как `<файл>.scri.bak`.

Что не удалось перенести точно — потерянные связи, пустые тексты, неизвестные типы
сущностей, синтезированные линии — перечисляется в `ProjectLoadResult.Warnings`
и показывается в строке состояния (событие `ProjectImported`).

Отдельно перечисляются поля `data`, к которым импортёр не обращался: список
собирается по факту чтения, а не по заранее заданному перечню, поэтому новое поле
из следующей сборки раннего приложения попадёт в предупреждение само, без правки
импортёра. Значения таких полей остаются в оригинале `.scri.bak`.

## Версия схемы 2: персонажи и этапы линий

Схема `.scri` обновлена до версии 2 (ADR 010). Добавлены таблицы:

| Таблица | Содержимое |
| --- | --- |
| `character` | Персонаж: `project_id`, `name`, порядок и `data_json` с карточкой целиком |
| `plot_line_stage` | Этап линии: `plot_line_id`, `title`, порядок и `data_json` (участники, сцены, признак финала) |

Карточка персонажа состоит из десятков свободных текстовых полей, поэтому она хранится
JSON-документом, а колонками описан только порядок и поиск. Этапы линий лежат отдельно от
`plot_line` и прикрепляются к линии по `plot_line_id`.

Миграция 1 → 2 только создаёт таблицы, поэтому файл версии 1 открывается без потерь:
структура и тексты остаются на месте, а перед подменой файла создаётся резервная копия
`<файл>.scri.bak`.

Стратегия записи — **полный снимок во временный файл с последующей заменой**:

1. Снимок восстановления сериализуется в `<project>.scri.recovery` (до записи).
2. Новая база пишется целиком во **временный** файл рядом с целевым.
3. Если включены резервные копии, существующий файл копируется в `.bak`.
4. Временный файл заменяет целевой через `File.Replace`.
5. Снимок восстановления удаляется только после успешной замены.

Открытая база никогда не подменяется «на месте» и WAL не используется
(`journal_mode = DELETE`, `Pooling = false`). Это зафиксировано в
`docs/decisions/002-sqlite-write-strategy.md`.

## Таблицы

| Таблица | Назначение |
| --- | --- |
| `schema_info` | Одна строка: версия схемы, версия приложения, время обновления |
| `project` | Метаданные проекта и `settings_json` |
| `series` | Серии проекта: заголовок, порядок, аудит |
| `book` | Книги серии: `project_id`, `series_id`, заголовок, порядок, аудит |
| `chapter` | Главы книги: `book_id`, заголовок, описание, порядок, аудит |
| `scene` | Сцены главы: `chapter_id`, статус, `revision`, `metadata_json`, порядок, аудит |
| `scene_document` | Канонический документ сцены (`document_json`) |
| `scene_version` | Сохранённые варианты: `id`, `scene_id`, полный снимок `data_json` |
| `plot_line` | Сюжетные линии проекта и связанные сцены (`scene_ids_json`) |

Каждая сущность структуры хранит аудит: `created_at`, `updated_at`, `is_deleted`,
`deleted_at`. Удаление — мягкое (ТЗ п. 10). Идентификаторы — `Guid` в текстовом виде;
связи хранятся только идентификаторами.

## Документ сцены

`scene_document.document_json` — каноническая модель `RichDocument` (ТЗ п. 37):

### Метаданные сцены

`scene.metadata_json` хранит пользовательские метаданные сцены (`SceneMetadata`):
точку зрения, место, время истории, заметки, теги и отметку `isKey` (ключевая сцена).
Добавление `isKey` схему не меняло: поле лежит внутри существующего JSON и в старых
файлах просто отсутствует (тогда считается `false`).

### Объём сцены

Объём в словах **не хранится** в файле: `Scene.Words` — производное значение. Он считается
при открытии проекта (документы уже прочитаны) и пересчитывается при каждой правке текста.
Поэтому число слов на карте книги и в редакторе всегда совпадает, а схема остаётся прежней.

```json
{
  "version": 1,
  "blocks": [
    {
      "id": "…guid…",
      "kind": "paragraph",
      "alignment": "left",
      "indentLevel": 0,
      "spans": [
        { "text": "Текст сцены", "format": "bold" }
      ]
    }
  ]
}
```

Правила:

- переводы строк нормализуются в `\n`;
- неизвестные необязательные поля допускаются;
- неизвестная обязательная версия (`version`) отклоняется с ошибкой
  `UnsupportedDocumentVersion`;
- плоский текст, поиск, статистика и будущий экспорт используют одну проекцию
  (`RichDocument.ToPlainText()`);
- битый документ не уничтожает старое содержимое: запись идёт снимком с заменой.

Список блоков и флаги форматирования живут в `ScriSelfStudio.Core.Text`
(`RichDocument`, `TextBlock`, `TextSpan`, `BlockKind`, `TextAlignment`, `TextFormat`).

## Старый ZIP-формат и оформление сцены

Плоское поле `text` хранит только текст. Документ сцены с оформлением и редактурой
дополнительно пишется в `content.json` → `scriself`. Для совместимости сохраняются
прежние карты по `SourceId`, а рядом записываются канонические карты по Guid сцены:

```json
{
  "scriself": {
    "version": 1,
    "documents": {
      "scene_001": { "schemaVersion": 1, "blocks": [ /* ... */ ] }
    },
    "documentsBySceneId": {
      "d1b4cd43-e836-4dfe-b6cd-1a594170338f": { "schemaVersion": 1, "blocks": [ /* ... */ ] }
    },
    "sceneVersions": { "scene_001": [ /* снимки */ ] },
    "sceneVersionsBySceneId": {
      "d1b4cd43-e836-4dfe-b6cd-1a594170338f": [ /* снимки */ ]
    }
  }
}
```

Узел сцены в `chapters[].scenes[]` хранит `id` для старых читателей и `scriselfId`
для канонических карт. Guid не зависит от главы или порядка сцены. При записи ID
сцен и глав уникальны во всём контейнере, включая несколько книг; отсутствующие
и повторяющиеся старые ID заменяются свободными ID на основе Guid.

Читатель сначала ищет запись по Guid, затем прежнюю запись по `SourceId`. Если один
старый ID относится к нескольким сценам и для них приходится использовать общий
документ или историю, файл отклоняется с предложением открыть резервную копию.
Повторяющийся `scriselfId` также является ошибкой. Это исключает подстановку текста
соседней сцены. Старый контейнер без карт читается из плоского `text`.

Studio 1.2.0 читает прежние карты, ранние сторонние приложения — плоский текст.
Канонические карты дополняют старые, поэтому переход не заменяет их ключи. Пустой
канонический документ сохраняется и применяется: он может содержать удалённые правки.

`scriself.version` — версия наших расширений, а не старого формата
(`manifest.version` остаётся 1). При чтении она не проверяется: поддерживаемые ключи
читаются по отдельности. Отсутствующий ключ допускается; повреждённый канонический
документ, история или редактура возвращают ошибку открытия. Для старого документа
без редактуры сохранён прежний запасной путь к плоскому тексту при порче оформления.
Новые карты добавлены без изменения версии ZIP или схемы SQLite.

## Версии сцен — схема 5

`Scene.Versions` содержит именованные снимки `SceneVersion`: ID, имя, дату UTC,
ревизию источника, признак страховочной копии и полный `RichDocument` с оформлением.
Это отдельная история, не счётчик конфликтов `Scene.Revision`. Миграция SQLite 4→5
создаёт таблицу `scene_version` и индекс по `scene_id` в копии базы. Предыдущий файл
остаётся в `.bak`; обычное последующее сохранение может обновить эту копию.
Старые сборки со схемой 4 не откроют новый SQLite-файл.

В ZIP история хранится в `content.json` → `scriself` → `sceneVersionsBySceneId`:
объект с Guid-ключами и массивами снимков. Параллельная карта `sceneVersions` с
прежними ключами сохраняет совместимость. Правила выбора карты и отказа при
неоднозначности те же, что для документов выше.
Отсутствие раздела означает пустую историю. Повреждённые снимки приводят к ошибке
открытия, а не к молчаливому стиранию истории. Старые сторонние приложения могут
потерять расширение при пересохранении, поэтому проверять их следует на копии.

Recovery включает версии в общий снимок проекта. Экспорт использует только текущие
документы сцен. Автоматической очистки истории нет; размер книги растёт с числом
версий. Подробнее: ADR 031.

## Версия схемы и миграции

- Текущая версия — `SchemaVersion.Current` (сейчас `6`; версия приложения в исходниках — 1.2.0).
- Поддерживаемый диапазон — `[SchemaVersion.MinimumSupported, SchemaVersion.Current]`.
- Файл с будущей версией отклоняется как неподдерживаемый.
- Миграция выполняется по копии, последовательными шагами в транзакциях
  (`ProjectMigrations`); при ошибке исходный файл остаётся нетронутым.
- Каждая несовместимая версия получает шаг миграции и regression-тест (ТЗ п. 59).

## Восстановление

Перед каждым сохранением создаётся снимок восстановления. Если приложение было
закрыто аварийно, при следующем открытии файла снимок обнаруживается
(`DetectRecoveryAsync`) и пользователю предлагается открыть, сохранить как или удалить
восстановление (ТЗ п. 27, 28). Сохранение пишет глубокую копию и запоминает ревизию.
Снимок удаляется после успешной записи только при отсутствии новых правок; иначе
recovery обновляется актуальной копией, а проект остаётся несохранённым (ADR 035).
Отпечаток внешне изменённого файла проверяется до записи recovery, чтобы устаревший
владелец не заменил данные восстановления другого экземпляра.

## Что запрещено

- Тихо подменять повреждённый проект пустым (silent fallback) — запрещено (ТЗ п. 26).
- Перезаписывать исходный файл до успешной проверки и создания резервной копии.
- Использовать WAL при подмене файла.
- Хранить связи объектами вместо идентификаторов.
