Цель проекта
Создать ScriSelf Studio для Windows на C# + Avalonia: офлайн‑редактор писательских проектов с книгами, главами, сценами, текстовым редактором, картой структуры, сюжетными линиями, настройками, автосохранением и восстановлением.

Архитектура solution  
- ScriSelfStudio.App — запуск и DI.
- ScriSelfStudio.Contracts — интерфейсы и DTO между модулями.
- ScriSelfStudio.Core — модель книги, сцены, текст, сериализация, события.
- ScriSelfStudio.BookArchitecture — книги → главы → сцены.
- ScriSelfStudio.EditorEngine — текст, форматирование, поиск, undo/redo.
- ScriSelfStudio.Launcher — проекты, настройки, открытие/создание.
- ScriSelfStudio.EditorUI — Avalonia Views/ViewModels редактора.
- ScriSelfStudio.ArchitectureUI — Avalonia UI структуры книги.

Правила работы ИИ
Каждый ИИ работает только в своей папке и через Contracts; UI не обращается к базе напрямую, движок не знает Avalonia, ядро не знает UI. Перед изменением контракта агент обязан описать изменение и обновить тесты. После каждой задачи обязательны: dotnet build, dotnet test, проверка запуска приложения и краткий отчёт: изменённые файлы, что проверено, что осталось.

13. Хранилище и безопасность данных
    - Основное хранилище — SQLite внутри .scri.
    - Запись выполняется атомарно через временный файл.
    - Перед заменой создаётся резервная копия.
    - При ошибке старый проект остаётся нетронутым.
    - Recovery хранится отдельно и удаляется только после успешного сохранения.
    - Версия схемы обязательна; для каждой несовместимой версии нужна миграция.
14. Avalonia UI
    - Использовать MVVM.
    - View содержит только AXAML-разметку и визуальные состояния.
    - ViewModel вызывает сервисы из Contracts.
    - Бизнес-логика запрещена в code-behind.
    - Все команды должны иметь состояние CanExecute.
    - Диалоги ошибок, подтверждения удаления и несохранённых изменений обязательны.
    - Тема, размеры, цвета и шрифты задаются через общие ресурсы.

Для каждой ветки и каждого агента запускать:

- создание книги, главы и сцены;
- ввод и сохранение текста;

21. Выбор компонента текстового редактора — до основной разработки
Avalonia сама по себе не гарантирует готовый редактор уровня Word. До реализации движка нужно проверить выбранный компонент на небольшом прототипе:
- форматирование непосредственно в редактируемом тексте;
- выделение, клавиатурную навигацию, кириллицу и emoji;
- вставку из Word, работу буфера обмена;
- undo/redo текста и форматирования;
- лицензию и возможность распространения.
Результат — зафиксированный выбор компонента и контракт адаптера. Нельзя поручать ИИ разработку собственного текстового движка без оценки этой задачи.
22. Уточнение контрактов и владения состоянием
Интерфейсы из пункта 7 — предварительный эскиз, а не готовое задание для реализации.
- Сервис проекта владеет открытым проектом; UI получает снимки данных и отправляет команды.
- Сессия редактора привязана к конкретной сцене.
- Изменения выполняются через операции вставки, удаления и форматирования; замена всего текста не должна быть основным способом редактирования.
- Контракты определяют ошибки, отмену операций, версию документа и единицы текстовых смещений.
- История отмены имеет одного владельца: компонент и движок не должны вести две независимые истории.
23. Уточнение сохранения и проверок
Для SQLite необходимо выбрать одну согласованную стратегию: транзакции в открытой базе либо сохранение полного снимка через временный файл. Подменять открытую базу с активным WAL нельзя.
Каждое сохранение привязано к версии документа. Завершение старой фоновой записи не снимает признак несохранённых изменений с более новой версии.
Также исправление сценария из пункта 18: сохранность текста проверяется после перезапуска, а undo/redo — внутри текущей сессии. Сохранение истории отмены между запусками в MVP не требуется.

События используются для обновления независимых модулей:

- ProjectClosed

- BookChanged
- ChapterChanged
- SceneChanged
- EditorDocumentChanged

События должны быть короткими, сериализуемыми при необходимости и содержать идентификаторы объектов. Событие не должно передавать целый View или ссылку на UI.
26. Ошибки и пользовательские сообщения
Внутри системы ошибки типизированы:
- ProjectNotFound
- ProjectFormatInvalid
- SchemaMigrationFailed

Для пользователя показывается понятное сообщение и следующее действие. Техническая причина пишется в лог. Silent fallback на пустой проект запрещён.

Каноническая модель:
{
  "version": 1,
  "blocks": [
    {
      "style": "paragraph",
      "alignment": "left",
      "runs": [
        {
          "text": "Текст сцены",
          "marks": ["bold"]
        }
      ]
    }
  ]
}
Правила:
- внутри модели переводы строк нормализуются в LF;
- неизвестные необязательные поля допускаются;
- неизвестная обязательная версия отклоняется;
- plain-текст получается через projection;
- поиск, статистика и экспорт используют один projection;
- битый документ не должен уничтожать старое содержимое.

59. Тестовые данные и регрессии
В репозитории хранится небольшой набор искусственных проектов:
- пустой проект;
- книга с несколькими главами и сценами;
- текст с кириллицей, emoji и комбинируемыми символами;
- документ с форматированием;
- большой проект;
- повреждённый файл;
- проект старой поддерживаемой версии;
- проект с неподдерживаемой будущей версией.
Реальные рукописи пользователя не включаются в тесты без его разрешения. Каждая исправленная ошибка потери данных получает регрессионный тест.
